Product Overview and Functional Spec
Project Name: Managent
Document Version: Current Implementation

1. Product Summary

Managent is an MCP gateway and control plane for teams running AI agents against real tools.

It gives agents one northbound MCP endpoint, fans out to downstream MCP servers and adapters, and enforces runtime controls before a tool call is allowed to execute.

Today the product is usable as a self-hosted control plane with:

- MCP tool federation
- agent-scoped bearer keys
- MCP registry and marketplace install flow
- ordered policy enforcement
- approval-required execution path
- encrypted mcp secret storage
- audit logging
- dashboard login/signup and session-based access

2. Current User Workflows

### Workflow A: Bring an agent online

1. Sign up or log in to the dashboard.
2. Create an agent.
3. Issue that agent a bearer key.
4. Configure the external agent or MCP client to call Managent's `/mcp` endpoint with that bearer key.

### Workflow B: Install an MCP

1. Open the MCPs page.
2. Choose a marketplace entry or add a custom MCP manually.
3. Attach the MCP to an existing agent.
4. Test the connection.
5. Save it and let the gateway synchronize its tools.

### Workflow C: Control access with policy

1. Open the Policies page.
2. Select an MCP.
3. Select one of that MCP's tools.
4. Create an ordered rule with:
   - effect: `allow`, `deny`, or `require_approval`
   - optional field/operator/value condition
   - optional rate limit
   - optional approval channel override

### Workflow D: Review activity

1. Open Logs.
2. Filter by search text, decision, or agent.
3. Export the current slice as CSV if needed.

3. Functional Modules

## Module 1: Northbound MCP Gateway

Current implementation:

- HTTP MCP endpoint at `/mcp`
- SSE-compatible endpoint at `/mcp/sse`
- bearer-token auth for MCP clients
- unified `tools/list` from all connected downstream MCPs
- namespaced tool calls routed back to the correct downstream system

Current constraint:

- protocol coverage is practical but not marketed as exhaustive conformance hardening

## Module 2: Downstream MCP and Adapter Layer

Current implementation:

- downstream transports: `stdio`, `http`, `sse`
- REST adapter mode for non-MCP HTTP targets
- persistent MCP records stored in Postgres
- marketplace catalog for prefilled installs
- tool snapshots persisted and reloaded

Current constraint:

- the Docker gateway image does not bundle third-party stdio MCP binaries

## Module 3: Policy and Approval Control

Current implementation:

- ordered policy rules
- subject targeting by agent or tag
- tool pattern matching
- action matching
- simple condition matching by field/operator/value
- rate-limit syntax such as `10/m`
- `allow`, `deny`, and `require_approval`
- pending approval persistence
- webhook-based approval resolution with signature verification

Current constraint:

- there is no dedicated pending-approvals dashboard view yet
- runtime state is not Redis-backed

## Module 4: Authentication and Identity

Current implementation:

- agent bearer keys for MCP traffic
- dashboard signup/login with user sessions
- optional admin bearer token for control-plane API access
- control-plane routes accept either the admin token or a logged-in session

Current constraint:

- client-facing gateway credentials are still long-lived bearer keys rather than short-lived proxy tokens

## Module 5: Secret Handling

Current implementation:

- encrypted storage for mcp secrets when a mcp secret key is configured
- secret env/header fields for mcp configuration
- request-time credential injection middleware

Current constraint:

- the system does not yet model the full short-lived token swap design from the original aspirational PRD

## Module 6: Observability and Admin UX

Current implementation:

- audit logs stored in Postgres
- overview dashboard
- agent management
- MCP registry and marketplace page
- policy creation and test mode
- approval integration settings
- audit log filtering and CSV export

Current constraint:

- audit storage is operational OLTP storage, not a dedicated analytical event store

4. Supported Deployment Model

The product currently supports self-hosted container deployment with Docker Compose.

The recommended first-time setup is:

1. Copy `.env.example` to `.env`
2. Set `MANAGENT_MCP_SECRET_KEY`
3. Run `docker compose up -d --build`
4. Open the dashboard on port `3000`
5. Use login/signup to access the control plane

5. External Integrations in the Current Build

Marketplace entries currently include:

- GitHub MCP
- Linear
- Stripe

Approval integration records currently support:

- Slack
- Discord

These are implemented as control-plane records plus signed webhook callbacks. The dashboard does not yet provide a full approval queue.

6. Known Product Boundaries

The current product intentionally stops short of a few ambitions that earlier docs implied:

- no Redis-backed runtime state
- no ClickHouse audit backend
- no short-lived proxy-token issuance system
- no bundled third-party stdio binaries in the Docker gateway image
- no dashboard approval inbox/resolution surface

7. Success Criteria for the Current Product

The current implementation is successful when a team can:

1. deploy the stack with Docker
2. create an agent and issue a key
3. install or add an MCP
4. see tools federated through `/mcp`
5. apply an allow/deny/approval policy to those tools
6. review resulting audit activity in the dashboard
